# 03. Codex 루프 엔지니어링

하네스(02 문서)가 "에이전트가 일하는 환경"이라면, 루프는 **"일을 어떤 주기로 돌리고, 어디서 멈추고, 어디서 사람이 개입하는가"** 다.
좋은 루프의 조건은 세 가지다.

1. **매 반복마다 객관적인 신호가 있다** (verify 통과/실패, 리뷰 차단 항목 수).
2. **멈출 조건이 명시되어 있다** (성공, 반복 횟수 초과, 결정 필요).
3. **실패가 다음 반복의 입력이 된다** (실패 로그·리뷰 결과·교훈이 다음 프롬프트와 하네스에 반영).

이 프로젝트에는 네 겹의 루프가 있다.

```text
[운영 루프]  출시 후 — 오류·CS·결제 불일치 → 버그 카드          (일~주)
  [개선 루프]  하네스 자체 개선 — 반복 실수 → 테스트/규칙/스킬     (주)
    [기능 루프]  카드 1장 — spec → 구현 → 검증 → 리뷰 → 병합      (시간~일)
      [내부 루프]  에이전트 내부 — 수정 → 테스트 → 수정            (분)
```

## 1. 내부 루프 — 에이전트 혼자 도는 루프

에이전트가 코드를 고치고 테스트로 확인하는 가장 안쪽 루프. 사람은 개입하지 않지만 **규칙은 하네스로 정해 준다.**

규칙(작업 카드 `제약`이나 AGENTS.md에 넣는다):
- 버그 수정은 **실패하는 테스트를 먼저** 작성하고 그 테스트가 실패하는 것을 확인한 뒤 고친다.
- 반복 중에는 `verify -Fast`나 관련 테스트 파일만 실행하고, 완료 직전에 전체 `verify`.
- **같은 실패로 3회 연속 수정이 실패하면 멈추고 보고**한다(원인 가설, 시도한 것, 막힌 지점). 계속 시도하면 테스트를 약화시키거나 엉뚱한 곳을 고치는 경향이 생긴다.
- 테스트 기대값 변경, 테스트 삭제·skip은 spec 변경이 근거일 때만 하고 보고서에 명시.
- 범위 밖 파일을 고쳐야 할 것 같으면 고치지 말고 보고.

훅으로 강제하는 부분(02 문서 4.11):
- **시작**: `main`에서 파일을 수정하려 하면 `PreToolUse` 훅이 거부하고, Codex는 작업 내용에 맞는 이름으로 브랜치를 만든 뒤 다시 시도한다. 브랜치를 자동으로 만들지는 않는다.
- **끝**: 변경이 있는 턴이 끝나면 `Stop` 훅이 `verify -Fast`와 보호 경로·테스트 동반 여부를 점검하고, 실패하면 사유를 새 지시로 돌려 한 번 더 고치게 한다. 위의 "3회 실패 시 멈춤"은 이 자동 연장을 포함해 센다.

## 2. 기능 루프 — 작업 카드 1장을 끝내는 루프

이 프로젝트의 기본 개발 단위. 기존에 `docs/superpowers`에서 하던 spec → plan → 구현 흐름을 정식 루프로 만든다.

```text
 ① 카드 선택 ─▶ ② spec 작성 ─▶ ③ [사람] spec 승인 ─▶ ④ plan·계약 확정
                                                         │
     ⑨ [사람] 수동 확인·병합 ◀─ ⑧ 수정 ◀─ ⑦ 리뷰 ◀─ ⑥ verify ◀─ ⑤ 구현(병렬)
                                   └────── 차단 항목 있으면 ⑤로 ──────┘
```

| 단계 | 누가 | 입력 | 출력 | 통과 조건 |
| --- | --- | --- | --- | --- |
| ① 카드 선택 | 사람 (자동 루프에서는 `agent:ready` 라벨) | `04-작업-카드-백로그.md` → GitHub 이슈 | 이번 카드 | 선행 카드 완료, 결정 항목 해결됨 |
| ② spec | Codex(메인) | 카드 + 로드맵 + 관련 코드 | `docs/specs/YYYY-MM-DD-<기능>.md` | 범위·제외·API 예시·완료 기준·테스트 목록 포함 |
| ③ 승인 | **사람** | spec | 승인 또는 수정 요청 | 결정이 필요한 부분이 없음 |
| ④ plan·계약 | Codex(메인) | spec | `docs/plans/...md`, 스키마·라우터 시그니처, OpenAPI 스냅샷 | 프런트/백엔드 작업이 독립적으로 나뉨 |
| ⑤ 구현 | backend_dev, frontend_dev | plan + 계약 | 각자 브랜치(또는 worktree)의 커밋 | 각 폴더 테스트 통과 |
| ⑥ verify | 메인 | 통합 브랜치 | `VERIFY PASS/FAIL` | 전체 통과 |
| ⑦ 리뷰 | reviewer(새 컨텍스트) | spec + diff | 차단/권고 목록 | 차단 0건 |
| ⑧ 수정 | 구현 에이전트 | 리뷰 결과 | 수정 커밋 | ⑥ 재통과 |
| ⑨ 확인·병합 | **사람** | 요약 보고, 수동 확인 목록 | main 병합 | 사람이 서버를 띄워 핵심 흐름 확인 |

운영 요령:
- **카드 하나는 작게.** 리뷰 가능한 크기(대략 변경 수백 줄, 하루 이내)로. 크면 ②에서 카드를 쪼갠다.
- **결제·인증·환불·권한 카드는 ⑦ 리뷰를 생략하지 않는다.** 나머지는 작으면 생략 가능.
- 백엔드만 있는 카드는 ⑤에서 backend_dev 하나만 쓴다. 에이전트를 많이 띄운다고 빨라지지 않는다. 계약이 확정되어 있을 때만 병렬이 이득이다.
- ⑨의 수동 확인은 "무엇을 클릭해서 무엇이 보여야 하는지" 목록으로 Codex가 작성해 보고하게 한다.

### 단계별 프롬프트 골격

기존 `docs/user_prompt.md` 형식(목표/맥락/제약/검증)을 그대로 쓴다.

**② spec 요청**
```markdown
# 목표
04-작업-카드-백로그.md의 <카드 ID> spec 작성. 구현은 하지 마.
# 맥락
@docs/01-기능-로드맵.md <해당 절>, @docs/decisions/<관련 ADR>, 관련 코드 경로
# 제약
결정이 필요한 항목은 임의로 정하지 말고 '질문' 절에 모아.
# 출력
docs/specs/<날짜>-<기능>.md: 범위, 제외, 데이터 변경, API 요청/응답 예시, 화면 상태, 완료 기준, 테스트 목록, 질문
```

**⑤ 구현 요청**
```markdown
# 목표
@docs/specs/<spec> 와 @docs/plans/<plan> 구현
# 제약
- backend_dev는 app/, tests/만, frontend_dev는 frontend/만 수정
- 계약(docs/api/openapi.json)을 바꿔야 하면 멈추고 보고
- 같은 실패 3회면 멈추고 보고
# 검증
scripts/verify.ps1 전체 통과 후, 변경 요약·추가 테스트 목록·수동 확인 목록 보고.
docs/harness/progress.md 갱신.
```

**⑦ 리뷰 요청**
```markdown
reviewer 에이전트로 main..HEAD 변경을 @docs/specs/<spec> 기준으로 검토.
코드 수정 금지. 차단/권고로 분류, 파일:줄과 재현 시나리오 포함.
```

## 3. 자동 반복 루프 — GitHub 이슈 → PR (Python + Codex SDK)

기능 루프 가운데 사람이 개입할 필요가 없는 구간(⑤~⑧)과 git·GitHub 작업은 Python 프로그램이 Codex SDK(`openai-codex`)를 호출해 자동화한다. 설계 전체는 **[05-github-이슈-자동화-루프.md](05-github-이슈-자동화-루프.md)**에 있다. 하네스 정비(H-1~H-6)를 끝낸 뒤에 도입한다. **verify가 없으면 자동 루프는 실패를 성공으로 착각한 채 계속 돈다.**

```text
[사람] 이슈 작성 + agent:ready
  → [루프] 이슈 선택 → worktree·브랜치 → Codex 구현 스레드 → verify(루프가 직접 실행)
         → Codex 리뷰 스레드(읽기 전용) → diff 가드 → 커밋·푸시 → PR 생성(Closes #N)
  → [사람] PR 검토 (/agent 댓글로 수정 요청하면 루프가 같은 스레드를 재개해 반영)
  → [사람] 머지 → [루프] 정리 후 다음 이슈
```

기능 루프 단계와의 대응:

| 기능 루프 | 자동 루프에서 |
| --- | --- |
| ① 카드 선택 | `agent:ready` 라벨 + 우선순위 라벨 + `Depends on #N` 규칙으로 루프가 선택 |
| ②③ spec·승인 | 큰 기능은 **spec 이슈**로 먼저 처리 → spec PR 머지가 곧 승인 |
| ⑤ 구현 | Codex 구현 스레드(`workspace_write`, `cwd`=worktree, `output_schema`로 결과 구조화) |
| ⑥ verify | 루프가 `scripts/verify.ps1`을 직접 실행, 실패 로그를 같은 스레드에 전달(최대 3회) |
| ⑦⑧ 리뷰·수정 | 새 스레드(`read_only`)의 리뷰어 → 차단 항목을 구현 스레드에 전달(최대 2라운드) |
| ⑨ 확인·병합 | PR 검토와 머지는 사람. 머지가 다음 이슈의 시작 신호 |

### 자동 루프의 안전장치 (요약 — 상세는 05 문서 8절)

| 장치 | 이유 |
| --- | --- |
| verify 3회·리뷰 2회·PR 피드백 2회 상한, 이슈별 토큰 사용량 상한 | 비용 폭주와 테스트 약화 방지 |
| 이슈마다 별도 브랜치·worktree, **루프에는 머지 권한 없음** | 사람이 ⑨에서 최종 확인 |
| 소유자가 쓰고 `agent:ready`를 붙인 이슈만 처리, 소유자 댓글만 반영 | 결정 항목 임의 결정, 프롬프트 인젝션 방지 |
| 결제·인증·환불·마이그레이션은 `risk:high` 라벨 → PR에 수동 확인 항목 강조 | 금전·데이터 사고는 되돌리기 어려움 |
| diff 가드: 금지 경로(.env, *.db, workflows, 하네스), assert 삭제·skip 추가, 변경량 상한 | "테스트를 고쳐서 통과", 하네스 자기 수정 방지 |
| git·GitHub 조작은 Python만, Codex 프로세스에서 토큰 제거 | Codex에 저장소 쓰기 권한을 주지 않음 |
| `agent:pause` 라벨로 긴급 정지, 라벨과 `state.json`으로 재시작 시 복구 | 무인 운영 |
| 각 턴의 프롬프트·결과·verify 로그 보관 | 개선 루프의 재료 |

## 4. 개선 루프 — 하네스를 고치는 루프

에이전트가 같은 종류의 실수를 두 번 하면, 프롬프트에서 다시 말해 주는 것이 아니라 **하네스를 고친다.** 한 번 고친 하네스는 이후 모든 세션에 적용된다.

주기: 카드 3~5장마다, 또는 주 1회.

```text
① 수집: blocked 카드, 리뷰 차단 항목, 사람이 ⑨에서 발견한 문제
② 분류: 이 실수는 어디서 막았어야 했나?
③ 수정: 가장 강한 장치부터 선택
④ 기록: docs/harness/lessons.md
```

**강한 장치 순서** — 위쪽일수록 확실하다.

| 순위 | 장치 | 예 |
| --- | --- | --- |
| 1 | 실패하는 테스트·린트·verify 단계 | "관리자 API에 403 테스트 없음" → 모든 `/admin` 라우트를 순회하며 비관리자 403을 검사하는 테스트 1개 |
| 2 | 코드 구조 | 결제 확정을 service 함수 하나로 모아 다른 경로가 생길 수 없게 |
| 3 | 스킬 절차 | `payment-change` 스킬에 "중복 웹훅 시나리오" 단계 추가 |
| 4 | AGENTS.md 규칙 문장 | "프런트에서 금액을 계산해 서버로 보내지 않는다" |
| 5 | 작업 카드의 일회성 지시 | 이번 카드에만 해당하는 것 |

`lessons.md` 기록 예:

```markdown
## 2026-11-03 웹훅 핸들러가 서명 검증 전에 DB를 갱신
- 발견: reviewer 차단 항목 (P0-7)
- 원인: 스킬에 처리 순서가 없었음
- 조치: payment-change 스킬 3단계에 "서명 검증 → 결제 재조회 → 상태 전이" 순서 명시,
        서명 불일치 시 DB 변화 없음을 검사하는 테스트 추가 (tests/test_webhook.py)
```

AGENTS.md는 계속 길어지기 쉽다. 개선 루프 때 **규칙 문장을 테스트로 바꿀 수 있으면 바꾸고 문장은 지운다.**

## 5. 운영 루프 — 출시 후

| 신호 | 수집 위치 | 처리 |
| --- | --- | --- |
| 서버 오류 | 에러 추적(Sentry 등), 구조화 로그 | 재현 테스트를 포함한 버그 카드 → 기능 루프 |
| 결제 불일치 | 대사 스크립트(PortOne PAID vs DB READY) | **즉시 수동 처리**(수강권 부여) 후 원인 카드 |
| 수강생 문의 | 이메일·문의 폼 | 반복 문의는 FAQ 또는 기능 카드 |
| 퍼널 이탈 | 분석(상세 → 결제 시작 → 완료) | P1 개선 카드 |
| 의존성 취약점 | `pip-audit`, `npm audit` (verify 또는 CI 주기 실행) | 업데이트 카드 |

버그 카드는 반드시 "재현 테스트 먼저"로 시작한다. 운영 버그는 대부분 테스트가 없던 경로에서 나오므로, 고친 뒤 그 테스트가 남는 것 자체가 하네스 강화다.

## 6. 사람이 반드시 개입하는 지점 요약

| 지점 | 이유 |
| --- | --- |
| 결정 항목(01 문서 8절) | 비용·법·정책 판단 |
| spec 승인 | 잘못된 방향으로 빠르게 가는 것을 막음 |
| 결제·인증·환불·권한·마이그레이션 변경 병합 | 되돌리기 어려운 사고 |
| `agent:ready` 라벨 부착 | 자동 루프에 들어갈 작업을 사람이 고른다 |
| PR 머지(자동 루프의 다음 이슈 시작 신호), 배포, 운영 DB 마이그레이션 | 외부에 영향 |
| 실제 결제창·카카오 로그인·영상 재생 수동 확인 | 외부 서비스는 테스트에서 가짜로 대체되므로 |
| 개발 서버 실행 | 사용자 선호 |

## 7. 피해야 할 패턴

- **검증 없는 자동 반복**: verify가 없거나 약하면 루프는 품질을 올리지 않고 변경량만 늘린다.
- **한 프롬프트에 기능 여러 개**: 실패 원인이 섞여 내부 루프가 수렴하지 않는다.
- **구현 세션에서 자기 리뷰**: 새 컨텍스트의 reviewer를 쓴다.
- **계약 없이 프런트·백엔드 병렬 구현**: 통합 단계에서 필드 불일치 수정에 시간을 다 쓴다.
- **실패할 때마다 프롬프트만 길게**: 하네스(테스트·스킬)로 옮기지 않으면 다음 세션에서 같은 실수를 한다.
- **에이전트가 실제 `app.db`나 실제 결제 키로 확인**: 가짜 클라이언트와 격리 DB가 기본.
