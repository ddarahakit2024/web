# 04. 작업 카드 백로그

로드맵(01)과 하네스 정비(02)를 Codex에 넘길 수 있는 크기로 나눈 순서 목록이다.
각 카드는 03 문서의 **기능 루프**(spec → 승인 → 구현 → verify → 리뷰 → 병합)로 진행한다.

- **자동 루프를 쓰면 카드 하나 = GitHub 이슈 하나**다. 이슈 템플릿(05 문서 5절)에 카드 내용을 옮기고, 선행 카드는 `Depends on #이슈번호`로 쓴다.
- 상태: 이 표의 `상태` 열 대신 GitHub 라벨이 원본이 된다. `todo`(이슈 없음/라벨 없음) → `agent:ready` → `agent:working` → `agent:pr-open` → 머지로 종료, 또는 `agent:needs-info` / `agent:blocked`
- 리뷰: **필수** = 이슈에 `risk:high` 라벨. 루프의 리뷰 에이전트를 통과해도 사람이 PR의 수동 확인 항목을 직접 확인하고 머지
- 결정: 01 문서 8절의 결정 항목 중 먼저 정해야 하는 것. 정해지기 전에는 `agent:ready`를 붙이지 않는다
- **0단계(H-*) 카드는 루프에 넣지 않는다.** 루프가 기대는 하네스이므로 Codex와 대화형으로 진행한다

## 카드 작성 예시 — E-1

Codex에 spec 작성을 요청할 때 아래처럼 카드를 펼쳐 쓴다(기존 `docs/user_prompt.md` 형식). 자동 루프에서는 같은 내용을 이슈 템플릿의 각 칸에 나눠 적는다. spec 이슈의 PR(`docs/specs/...md` 추가)이 머지되면, 구현 이슈를 새로 만들어 맥락에 그 spec을 링크하고 `Depends on #<spec 이슈>`를 적는다.

```markdown
# 목표
수강권(Enrollment) 도입. 결제 확정 시 수강권이 생기고, 내가 수강 중인 강의를 조회할 수 있다.
이번 요청은 spec 작성까지만. 구현하지 마.

# 맥락
@docs/01-기능-로드맵.md (P0-6, P0-7), @docs/decisions/D2-수강기간.md
@app/api/routers/payments.py, @app/models/payment_order.py, @tests/test_payments.py

# 제약
- 결제 확정 로직은 service 함수 하나로 모으고 confirm API가 이를 호출 (이후 웹훅도 같은 함수 사용 예정)
- 스키마 변경은 Alembic 리비전으로
- (user_id, course_id) 활성 수강권은 하나만
- 기존 결제 API 응답 형식 유지

# 완료 기준 (spec에 포함할 것)
- 결제 확정 1회당 수강권 1개, 같은 주문으로 confirm 2회 호출해도 1개
- 무료(0원) 강의는 결제 없이 수강 신청 가능
- GET /me/courses: 비로그인 401, 다른 사용자 수강권 미노출
- GET /courses/{id}: 로그인 사용자는 enrolled 여부 포함

# 검증
scripts/verify.ps1 전체 통과
```
