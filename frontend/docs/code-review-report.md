- 검토일: 2026-10-20
- 범위: `frontend/src`와 `app`의 인증·프로필 흐름 및 관련 테스트
- 방식: 프론트엔드와 백엔드 서브에이전트가 각각 읽기 전용으로 검토하고, 결과를 통합했습니다.

## 요약

현재 인증 요구사항인 JWT의 HttpOnly 쿠키 전달, 로그인 성공 후 메인 페이지 이동, 쿠키 기반 프로필 조회와 헤더 표시가 구현되어 있습니다. 다만 운영 환경에서의 JWT 서명 키 설정, Python 버전 호환성, 로그아웃 처리와 프로필 조회 상태 처리를 보완하는 것이 좋습니다.

## 우선 수정 권고

### 높음 — 기본 JWT 키가 고정값이며 `.env` 자동 로딩도 없음

- 위치: [`app/core/config.py:4`](../../app/core/config.py#L4)
- 문제: `JWT_SECRET_KEY`가 환경 변수에 없으면 코드에 공개된 개발용 문자열을 사용합니다. 이 키로 서명된 JWT는 소스 코드를 아는 사람이 위조할 수 있습니다. 또한 현재 설정 코드는 `.env` 파일을 직접 읽지 않고 `os.getenv()`만 사용합니다.
- 권고: 개발용 키를 운영 기본값으로 허용하지 말고, 운영 환경에서 충분히 강한 키가 없으면 시작 단계에서 실패하도록 하세요. 서버 실행 때 `.env`를 명시적으로 로드하거나 배포 환경의 비밀값 주입을 보장하고, 설정 누락 검증을 추가하세요.

### 보통 — 프로필 조회 중 로그인 버튼이 잠시 보이고 조회 오류를 로그아웃으로 취급

- 위치: [`frontend/src/PostList.vue:100`](../src/PostList.vue#L100), [`frontend/src/PostList.vue:144`](../src/PostList.vue#L144)
- 문제: 프로필 조회가 끝나기 전 `profile`은 `null`이어서 로그인 링크가 표시됩니다. 네트워크 오류나 서버 오류도 모두 비로그인 상태와 동일하게 처리됩니다.
- 권고: 로딩, 인증됨, 비로그인, 조회 오류 상태를 구분하세요. 로딩 중에는 계정 버튼 표시를 보류하고, 조회 오류에는 재시도나 오류 상태를 제공하면 로그인 링크가 깜빡이거나 서버 장애를 로그아웃으로 오인하는 일을 줄일 수 있습니다.

### 보통 — `Partitioned` 쿠키가 Python 3.14 미만에서 호환되지 않을 수 있음

- 위치: [`app/core/session.py:19`](../../app/core/session.py#L19)
- 문제: 현재 실행 환경(Python 3.14.8, Starlette 1.9.0)에서는 지원되지만, Starlette의 `partitioned=True` 설정은 Python 3.14 미만에서 예외가 발생할 수 있습니다. 저장소의 의존성 설정에는 Python 최소 버전이 명시되어 있지 않습니다.
- 권고: Python 3.14 이상을 프로젝트 실행 요건으로 명시·검증하거나, 지원할 Python 버전에서 동작하는 쿠키 설정 경로를 제공하고 최저 지원 버전에서 테스트하세요.

### 보통 — HttpOnly 인증 쿠키를 만료시키는 로그아웃 경로가 없음

- 위치: [`app/api/routers/auth.py`](../../app/api/routers/auth.py), [`app/core/session.py`](../../app/core/session.py)
- 문제: HttpOnly 쿠키는 프론트엔드 JavaScript에서 직접 지울 수 없습니다. 현재 쿠키는 만료 시간까지 유효하며 로그아웃 동작이 없습니다.
- 권고: 로그아웃 API를 추가해 같은 쿠키 이름과 경로로 만료 쿠키를 응답하고, 프론트엔드에서 로그아웃 후 비로그인 화면 상태를 반영하세요. `Partitioned`, `Secure`, `SameSite` 속성도 발급 쿠키와 일치하도록 확인하세요.

### 브라우저 통합 검증

- 위치: 프론트엔드 `localhost:5173`에서 백엔드 `127.0.0.1:8000`으로 가는 자격 증명 요청
- 확인 한계: 서브에이전트는 서버를 실행하지 않았고 TestClient 테스트도 실행하지 않아, 실제 Chrome에서 `Secure; SameSite=None; Partitioned; HttpOnly` 쿠키가 저장·전송되는지는 이번 검토에서 확인하지 못했습니다. Chromium의 쿠키 단위 테스트는 HTTP `127.0.0.1`에서 `Secure` 쿠키를 허용하는 동작을 확인하지만, 앱의 실제 CORS·요청 흐름을 대체하지는 않습니다.
- 권고: 사용자가 서버를 실행한 뒤 Chrome DevTools Network/Application 패널에서 로그인 응답의 `Set-Cookie`, `/user/me` 요청의 `Cookie`, 응답 프로필을 확인하세요. [Chromium 쿠키 테스트](https://chromium.googlesource.com/chromium/src/%2B/refs/heads/main/net/cookies/cookie_store_unittest.h)

## 검토 중 제외한 항목

- 프론트엔드 오류 메시지가 깨져 있다는 의견은 파일을 UTF-8로 확인한 결과 한국어 문구가 정상 저장되어 있어 수정 권고에서 제외했습니다. PowerShell 콘솔 인코딩으로 인한 표시 문제로 판단했습니다.
- JWT가 JSON 응답이나 `localStorage`에 남는 문제는 두 에이전트 모두 찾지 못했습니다.

## 검증 기록

이번 검토는 읽기 전용으로 진행되어 에이전트들은 테스트나 서버를 실행하지 않았습니다. 직전 구현 검증에서는 백엔드 pytest 17개, 프론트 Jest 11개가 통과했고 Vite 빌드가 성공했습니다. 실제 브라우저 기반 인증 흐름은 아직 확인하지 않았습니다.
